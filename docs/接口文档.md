## 0. 实现模式

本项目提供两种实现同一套八个 `/api` 接口的服务：

- **Mock 开发模式**：在 `backend` 目录执行 `..\.venv\Scripts\python.exe -m mock_api`。它只使用进程内内存，不连接 MySQL、Neo4j、Ollama、FAISS 或 DashScope；`/api/health` 的六个字段均返回 `mock`，重启后会话清空。
- **真实联调模式**：执行 `..\.venv\Scripts\python.exe -m uvicorn api.chat_api:app --reload --port 8000`，需要完整的数据库、模型、索引和 `backend/.env` 配置。

两个服务都监听 `127.0.0.1:8000`，不能同时运行。前端只请求相对路径 `/api/*`，不包含 Mock 分支。本文档仍是字段、状态码和事件顺序的契约真相源；任何接口变更都必须同步修改真实实现与 Mock 实现，并重新执行 `frontend` 的 `npm run api:types`。

## 1. 通用规范

### 1.1 基础信息

| 项 | 值 |
| --- | --- |
| 协议 | HTTP/1.1 |
| 开发环境 Base URL | `http://127.0.0.1:8000` |
| API 前缀 | `/api` |
| 普通请求内容类型 | `application/json; charset=utf-8` |
| 流式响应内容类型 | `application/x-ndjson; charset=utf-8` |
| 字符编码 | UTF-8（**所有 JSON 序列化必须 `ensure_ascii=False`**，否则中文会变成 `\uXXXX` 转义，前端可读性差且体积膨胀） |
| 认证 | 无（单机单用户，不做账号体系，见 `需求分析.md` §3.2） |
| OpenAPI 版本 | 3.1（由 FastAPI 自动生成） |

### 1.2 URL 与命名规范

| 规则 | 示例 |
| --- | --- |
| 资源名用**复数**、**小写** | `/api/conversations` |
| 多词用**连字符**分隔，不用下划线 | `/api/ask-graph`（若将来拆分） |
| 层级关系用路径表达 | `/api/conversations/{conversation_id}/messages` |
| 路径参数用 `snake_case` | `{conversation_id}` |
| 查询参数用 `snake_case` | `?page=1&size=20` |
| JSON 字段用 `snake_case` | `conversation_id`、`created_at` |

> **字段命名与前端**：后端统一输出 `snake_case`。前端 TypeScript 保持 `snake_case` 不做转换 —— 转换层会引入「类型定义与实际字段不一致」的隐患，收益远小于成本。

### 1.3 请求与响应约定

**成功响应**

- 单个资源：直接返回对象本身，不套 `data` 外壳
- 集合资源：返回分页信封 `{ total, page, size, items }`（见 §1.4）
- 创建成功：`201 Created` + 新对象
- 删除成功：`204 No Content`，无响应体

**失败响应**（统一信封）

```json
{
  "code": 40401,
  "msg": "会话不存在",
  "detail": "conversation_id=9f1c3b2a-... 在 agentic_rag.conversation 中未找到"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | 业务错误码（见 §1.5），成功时为 `0` |
| `msg` | string | 面向用户的中文提示，可直接展示 |
| `detail` | string \| null | 面向开发者的技术细节，**必须携带真实异常类型与原文** |

> **`detail` 为什么必须保留原始异常**：这是本项目从既有 `cypher_tool` 修复中总结的教训。异常被吞成统一的 500 后，「连接失败 / 密码错误 / Cypher 语法错误」长得一模一样，排查时完全没有线索。

### 1.4 分页规范

**请求**：`?page=1&size=20`

| 参数 | 类型 | 默认 | 约束 |
| --- | --- | --- | --- |
| `page` | integer | 1 | ≥ 1 |
| `size` | integer | 20 | 1 ≤ size ≤ 100 |

**响应信封**：

```json
{
  "total": 12,
  "page": 1,
  "size": 20,
  "items": [ /* ... */ ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `total` | integer | 符合条件的**总条数**（非当前页条数），前端据此渲染分页器 |
| `page` | integer | 当前页码，原样回显 |
| `size` | integer | 每页条数，原样回显 |
| `items` | array | 当前页数据 |

### 1.5 错误码总表

| 业务码 | HTTP 状态 | 含义 | 前端处理建议 |
| --- | --- | --- | --- |
| `0` | 200 / 201 / 204 | 成功 | — |
| `40001` | 400 | 参数缺失或非法 | 高亮并聚焦出错的输入项 |
| `40401` | 404 | 会话不存在 | 从本地列表移除该会话，刷新列表 |
| `50001` | 500 | 向量库不可用（索引缺失） | 提示后端执行 `python utils/rag_index.py medical` |
| `50002` | 500 | 图谱不可用（连接或认证失败） | 提示检查 Neo4j 实例是否已启动 |
| `50003` | 502 | 云端模型不可用（超时 / 网络不通） | 提示检查网络后重试（本项目问答全走云端，已无本地模型可切换，见 `系统设计.md` ADR-8） |
| `50004` | 503 | 重排服务不可用 | **静默降级**，不打断用户（见下方说明） |

> **`50004` 是本项目唯一「不报错」的错误码。** 重排失败时链路自动降级为「混合检索 + RRF 融合」结果直接返回，对用户完全无感，仅在服务端日志记录。前端**不需要**为它写任何分支逻辑 —— 这正是把它设计成错误码而非异常的用意。

### 1.6 跨域（CORS）

开发期前端跑在 `5173`、后端在 `8000`，属于跨域。两种方案，**推荐第二种**：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| 后端开 CORS | `CORSMiddleware` 允许 `http://127.0.0.1:5173` | 简单，但演示期前后端分居两端口 |
| **Vite 代理**（推荐） | Vite `server.proxy` 把 `/api` 转发到 `8000` | 前端代码里只写相对路径 `/api/...`，**无跨域、无硬编码域名**，演示期换成单端口部署时零改动 |

**后端仍需配置 CORS**（作为兜底，例如直接用 `file://` 打开 HTML 调试时）。

## 2. 功能层级总览

接口按**业务功能域**分为三层。分层的依据是「谁在什么场景下调用」：问答域是用户每次提问都会走的**核心链路**，会话域是左侧边栏的**数据管理**，系统域是**部署与排障**用。

```
┌─────────────────────────────────────────────────────────────┐
│ L1 问答域  Ask                                                │
│   核心业务链路：提问 → 检索 → 溯源 → 用量                       │
│   POST /api/ask              医疗健康问答（流式）               │
│   POST /api/ask_graph        医疗疾病问答（流式）               │
├─────────────────────────────────────────────────────────────┤
│ L2 会话域  Conversation                                       │
│   数据管理：左侧会话列表与历史消息                              │
│   GET    /api/conversations              会话列表（分页）      │
│   POST   /api/conversations              新建会话              │
│   PATCH  /api/conversations/{id}         重命名会话            │
│   DELETE /api/conversations/{id}         删除会话（级联）      │
│   GET    /api/conversations/{id}/messages 历史消息             │
├─────────────────────────────────────────────────────────────┤
│ L3 系统域  System                                             │
│   运维排障：演示前跑一次                                       │
│   GET    /api/health                     依赖健康检查          │
└─────────────────────────────────────────────────────────────┘
```

| 层级 | 接口数 | 对应需求 | 响应形式 |
| --- | --- | --- | --- |
| L1 问答域 | 2 | F2 / F3 / F4 / F5 / F6 | **NDJSON 流式** |
| L2 会话域 | 5 | F4 / F5 / F7 | JSON |
| L3 系统域 | 1 | — | JSON |

## 3. L1 问答域

### 3.1 接口一览

| 方法 | 路径 | 说明 | 智能体 | 工具集 |
| --- | --- | --- | --- | --- |
| POST | `/api/ask` | 医疗健康问答 | `rag_agent` | `retrieve_context` |
| POST | `/api/ask_graph` | 医疗疾病问答 | `cypher_agent` | `cypher_tool` |

两者的差别在**绑定的智能体与数据源**：`/api/ask` 只检索医学文档并返回 `vector` 来源，`/api/ask_graph` 只查询知识图谱并返回 `graph` 来源。单次回答不得混入另一模式的来源。

两者的**模型相同**，均为云端 DashScope `qwen3-max` —— 本项目问答统一使用云端模型（本地 Ollama 只负责词嵌入，见 `系统设计.md` ADR-8）。

### 3.2 `POST /api/ask`

**请求体**

| 字段 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `question` | string | 是 | — | 用户问题，长度 1–2000 |
| `conversation_id` | string \| null | 否 | `null` | 传 `null` 则**新建会话**，服务端通过首行 `sid` 事件回传真实 ID；**续聊历史会话时必须传入**，否则上下文断裂（见 §3.6.3） |
| `use_memory` | boolean | 否 | `true` | `false` 时单轮问答不带历史上下文（见 §3.6.4） |

```json
{
  "question": "百日咳有哪些症状",
  "conversation_id": null,
  "use_memory": true
}
```

**响应**：`200 OK`，`Content-Type: application/x-ndjson; charset=utf-8`，事件流见 §3.4。

**错误**：见 §1.5。流已开始后发生的错误以 `err` 事件下发（而非 HTTP 状态码），因为此时响应头已发送，无法再改状态码。

### 3.3 `POST /api/ask_graph`

请求体与响应格式**完全同 `POST /api/ask`**，仅内部绑定的智能体不同。

**为什么不做成一个接口加参数？** 因为两者的**提示词、工具集、所用模型都不同**，合成一个接口会导致「同一个 URL 的行为依赖参数分支」，前端无法从 URL 判断该期待什么能力，也不利于分别限流与监控。保持两个端点，语义更清晰。

### 3.4 流式协议（NDJSON）详解

这是本文档**最重要的部分** —— 它是前后端唯一需要严格对齐的契约。

#### 3.4.1 为什么是 NDJSON

| 方案 | 优势 | 本项目为何不选 |
| --- | --- | --- |
| **NDJSON**（选中） | 一行一个 JSON，实现最简单；现有前端已基于 `fetch` + `ReadableStream` 实现 | — |
| SSE | 浏览器原生 `EventSource` 支持自动重连 | `EventSource` **只支持 GET，无法提交 JSON 请求体**；而本接口必须 POST |
| WebSocket | 双向通信 | 本场景是「一问一答」的单向流，双向能力用不上，还要额外处理心跳与重连 |

#### 3.4.2 事件类型完整表

每行是一个**独立的 JSON 对象**，行与行之间用 `\n` 分隔。

| 事件 | 载荷 | 出现时机 | 出现次数 | 前端处理 |
| --- | --- | --- | --- | --- |
| **`sid`** | `{"sid": "<uuid>"}` | **首行** | 0 或 1 次（仅新建会话时） | 记录会话 ID，后续请求携带 |
| **`content`** | `{"c": "<增量文本>"}` | 正文生成期间 | **多次** | 追加到当前气泡 |
| **`sources`** | `{"s": [Source, ...]}` | 正文结束后 | 0 或 1 次 | 渲染溯源卡片（F4） |
| **`usage`** | `{"u": Usage}` | **最后一行** | 0 或 1 次 | 渲染 token 用量（F5） |
| **`error`** | `{"err": "<描述>"}` | 任意时刻 | 0 或 1 次 | 红色提示，**收到后流终止** |

#### 3.4.3 事件顺序保证

```
sid?  →  c  c  c  ...  c  →  s?  →  u?
```

- `sid` 若出现，**必定是第一行**（前端可据此在流开始时就知道会话 ID）
- `c` 事件**至少一个**（除非发生错误）
- `s` / `u` 只在正文完全生成后出现，且**顺序固定：先 `s` 后 `u`**
- `err` 一旦出现，**该行之后不再有任何事件**，连接随后关闭
- 流的**正常结束由连接关闭标识**（`reader.read()` 返回 `done`），**不引入额外的 `done` 事件** —— 现有前端已按此实现

#### 3.4.4 完整报文示例

**场景**：新建会话，提问「百日咳有哪些症状」。

```
{"sid":"9f1c3b2a-4d5e-4f60-8a71-2b3c4d5e6f70"}
{"c":"百日咳"}
{"c":"的常见症状"}
{"c":"包括：阵发性痉挛性咳嗽、吸气性吼声、低热等。"}
{"s":[{"type":"graph","name":"Disease:百日咳 → DISEASE_SYMPTOM → Symptom","score":null,"snippet":"命中症状 7 条","meta":{"cypher":"MATCH (d:Disease {name:'百日咳'})-[:DISEASE_SYMPTOM]->(s:Symptom) RETURN s.name","row_count":7}},{"type":"vector","name":"百日咳","score":0.83,"snippet":"【预防】接种百日咳疫苗…","meta":{"channel":"hybrid","rerank_score":0.83,"dense_rank":2,"sparse_rank":5}}]}
{"u":{"prompt":512,"completion":128,"total":640,"model":"qwen3-max-2026-01-23","latency_ms":3210}}
```

**场景**：沿用已有会话，模型直接回答（未调用工具）。

```
{"c":"抱歉，我无法从现有资料中确认这个问题。"}
```

（无 `sid` —— 因为不是新建会话；无 `s` —— 因为没有调用工具；无 `u` —— 因为未走云端模型）

#### 3.4.5 溯源对象 `Source`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | `"vector"` \| `"graph"` | 来源通道：向量检索 / 图谱查询 |
| `name` | string | 来源名。图谱类形如 `Disease:百日咳 → DISEASE_SYMPTOM → Symptom` |
| `score` | number \| null | 相关度。**图谱类固定为 `null`**（图谱命中是确定性的，没有相似度概念） |
| `snippet` | string | 内容片段，前端可折叠展示 |
| `meta` | object \| null | 中间过程明细（见下） |

**`meta` 的字段随 `type` 变化**：

| `type` | `meta` 字段 | 含义 |
| --- | --- | --- |
| `vector` | `channel` | 检索通道：`hybrid` \| `dense` \| `sparse` |
| | `rerank_score` | 重排后的分数 |
| | `dense_rank` | 在稠密通道中的排名 |
| | `sparse_rank` | 在稀疏通道中的排名 |
| `graph` | `cypher` | 实际执行的 Cypher 语句 |
| | `row_count` | 命中行数 |

> **`meta` 保留中间过程的价值**：演示时能说清「这条答案为什么排第一」—— 稠密排第 2、稀疏排第 5、融合后进重排、最终得分 0.83。这是把黑箱变白箱的关键，也是答辩时最有说服力的材料。

#### 3.4.6 用量对象 `Usage`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `prompt` | integer | 输入 token 数 |
| `completion` | integer | 输出 token 数 |
| `total` | integer | 总 token 数（`prompt + completion`） |
| `model` | string | 实际调用的模型名 |
| `latency_ms` | integer | 端到端耗时（毫秒） |

> **本项目问答全走云端模型，因此 `u` 事件正常情况下每条回答都会出现**（实测 `model` 为 `qwen3-max-2026-01-23`）。
>
> 但协议上仍把它标记为**可选**（0 或 1 次），前端请按可选项处理 —— 这样将来若接入本地模型，前端不必改动。

#### 3.4.7 中止与超时

| 场景 | 表现 |
| --- | --- |
| 用户点「停止」 | 前端 `AbortController.abort()` 中断 fetch，**已接收的内容保留** |
| 服务端异常 | 下发 `{"err": "..."}` 后关闭连接 |
| 云端模型超时 | 下发 `{"err": "..."}`，错误码语义对应 `50003` |

### 3.5 前端流式消费参考实现

```ts
// 关键点已用注释标出，这些都是实际会踩的坑
export async function streamAsk(
  payload: AskRequest,
  onEvent: (e: StreamEvent) => void,
  signal: AbortSignal,
) {
  const res = await fetch('/api/ask', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload),
    signal,
  });

  if (!res.ok) {
    // 流尚未开始就失败，此时还能拿到 HTTP 状态码与错误信封
    throw new ApiError(await res.json());
  }
  if (!res.body) throw new Error('响应体为空，无法读取流');

  const reader = res.body.getReader();
  // ⚠️ 必须用 { stream: true }：中文是多字节 UTF-8，可能被切在两个 chunk 之间，
  //    不加这个参数会在字符中间截断，产生乱码。现有前端已正确处理，重写时别丢。
  const decoder = new TextDecoder();
  let buffer = '';

  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });

    // ⚠️ 按 \n 切分后，最后一段可能是"半行"，必须留在 buffer 里等下一个 chunk
    const lines = buffer.split('\n');
    buffer = lines.pop() ?? '';

    for (const line of lines) {
      const trimmed = line.trim();
      if (!trimmed) continue;
      try {
        onEvent(JSON.parse(trimmed));
      } catch {
        // ⚠️ 单行解析失败不能中断整个流，跳过即可
      }
    }
  }
}
```

### 3.6 记忆与会话续聊机制

**需求行为**：用户点击左侧任意历史会话，能直接接着聊，且模型**记得住前文的问答结果**。

#### 3.6.1 上下文的载体

智能体的对话上下文就是 LangGraph 状态里的**一个消息列表**：

```python
class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]   # ← 对话上下文列表
```

`add_messages` 是 reducer，节点返回的新消息会被**追加**而非覆盖，列表随对话自然增长。

#### 3.6.2 两条路径

```
POST /api/ask（带 conversation_id，即 thread_id）
        ↓
  checkpointer 里有该 thread 吗？
   ├── 有（热路径）→ 直接用内存中的 messages 列表，零数据库开销
   └── 无（冷启动）→ 从 MySQL 读全部历史 → 一次性回灌 → 再用
        ↓
  拼装 messages = [SystemPrompt] + 历史 + 新问题 → 跑 agent → 流式回答 → 落库
```

| 路径 | 触发条件 | 数据库开销 |
| --- | --- | --- |
| **热路径** | 同一会话连续提问 | **零** —— 完全走内存 |
| **冷路径** | 进程重启后首次打开某会话 | 一次 `SELECT`（读该会话历史） |

#### 3.6.3 前端完整时序

**场景：用户点击左侧的历史会话「百日咳的症状」，然后追问「那能吃什么」**

| 步骤 | 前端动作 | 接口 | 说明 |
| --- | --- | --- | --- |
| 1 | 点击会话项 | — | 拿到 `conversation_id` |
| 2 | 拉取历史消息 | `GET /api/conversations/{id}/messages` | 渲染出之前的问答，**此时输入框可用** |
| 3 | 用户输入「那能吃什么」并发送 | `POST /api/ask` | 请求体带 `conversation_id`，**不要传 `null`** |
| 4 | 接收流式事件 | — | 服务端内部完成冷启动回灌（前端无感） |
| 5 | 收到 `c` 事件 | — | 追加到气泡 |
| 6 | 收到 `s` / `u` 事件 | — | 渲染溯源卡片与 token 用量 |
| 7 | 流结束 | — | 刷新该会话的消息缓存（见 §8.5） |

**关键点**：**步骤 3 必须带 `conversation_id`**。若误传 `null`，服务端会**新建一个会话**，于是上下文断裂、追问答非所问 —— 这是这个功能最容易出的 bug。

#### 3.6.4 `use_memory` 参数的语义

| 取值 | 行为 |
| --- | --- |
| `true`（默认） | 携带历史上下文，模型能接上前文 |
| `false` | **单轮问答**，忽略历史。用于「这条问题我希望它独立回答」的场景 |

`use_memory=false` 时，服务端仍会把本轮问答写入数据库（保证历史完整），只是**不把历史喂给模型**。

#### 3.6.5 前端需要实现的三件事

1. **会话切换时清空当前流式状态** —— 若上一个会话的流还在进行，先 `abort()`，否则两个会话的回答会串台
2. **切换会话后重置本地状态** —— `answer` / `sources` / `usage` 全部清空，再渲染新会话的历史消息
3. **发送时带上 `conversation_id`** —— 见 §3.6.3 的关键点

```ts
// src/hooks/useChatStream.ts（片段）
const switchConversation = useCallback(async (conversationId: string) => {
  abortRef.current?.abort();            // 1. 中断上一个会话的流
  setAnswer(''); setSources([]); setUsage(null); setStatus('idle');  // 2. 重置本地状态
  const history = await unwrap(api.GET('/api/conversations/{conversation_id}/messages', {
    params: { path: { conversation_id: conversationId } },
  }));
  setMessages(history.items);           // 3. 渲染历史
  setConversationId(conversationId);    // 4. 记住当前会话，后续提问带上它
}, []);
```

#### 3.6.6 约束与注意事项

| 项 | 说明 |
| --- | --- |
| **单进程约束** | 内存记忆是**进程内**的。服务端以单 worker 运行；若将来改为多 worker，需换成持久化 checkpointer |
| **进程重启** | 重启后首次访问某会话会触发一次回灌，用户**无感知**（仅首次请求稍慢） |
| **删除会话** | 服务端会同步清理内存中的上下文，前端无需额外处理 |
| **上下文窗口** | 服务端在喂给模型前会裁剪超长上下文，但**数据库与前端展示的仍是完整历史** |
| **回灌范围** | 只回灌 `user` / `assistant` 两类消息，工具调用过程不进上下文 |

> 以上均为服务端内部机制，**前端只需按 §3.6.3 的时序调用接口即可**，不需要了解实现细节。此处写出来是为了让前端理解「为什么首次打开旧会话会稍慢一点」，以及排查问题时能定位。

## 4. L2 会话域

### 4.1 接口一览

| 方法 | 路径 | 说明 | 状态码 |
| --- | --- | --- | --- |
| GET | `/api/conversations` | 会话列表（分页，按最近更新倒序） | 200 |
| POST | `/api/conversations` | 新建会话 | 201 |
| PATCH | `/api/conversations/{conversation_id}` | 重命名会话 | 200 |
| DELETE | `/api/conversations/{conversation_id}` | 删除会话（级联删消息） | 204 |
| GET | `/api/conversations/{conversation_id}/messages` | 拉取历史消息（分页，按时间正序） | 200 |

### 4.2 `GET /api/conversations`

**查询参数**：`page`（默认 1）、`size`（默认 20，最大 100）

**响应 `200`**

```json
{
  "total": 12,
  "page": 1,
  "size": 20,
  "items": [
    {
      "id": "9f1c3b2a-4d5e-4f60-8a71-2b3c4d5e6f70",
      "title": "百日咳的症状",
      "agent_type": "rag",
      "message_count": 6,
      "total_tokens": 4820,
      "created_at": "2026-09-19T15:02:11+08:00",
      "updated_at": "2026-09-19T15:08:40+08:00"
    }
  ]
}
```

**排序**：按 `updated_at` **倒序**。数据库已建降序索引 `idx_updated_at (updated_at DESC)`，避免 filesort。

> **`message_count` 与 `total_tokens` 是冗余字段**（可由 `message` 表聚合得出）。冗余的原因是会话列表页要展示这两个数字 —— 不冗余的话每页 20 条就要跑 20 次聚合子查询。代价是写入时需同步更新 `conversation` 行，但本项目单用户、写少读多，这笔交易划算。

### 4.3 `POST /api/conversations`

**请求体**

| 字段 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `title` | string | 否 | `"新会话"` | 会话标题，最长 120 字符 |
| `agent_type` | `"rag"` \| `"graph"` | 否 | `"rag"` | 所属智能体 |

**响应 `201`**：返回完整会话对象（结构同 §4.2 的 `items` 元素）。

> **实际使用中很少主动调用这个接口** —— 前端直接 `POST /api/ask` 且 `conversation_id` 传 `null`，服务端会自动建会话并通过 `sid` 事件回传 ID。本接口主要用于「点新建按钮时先建一个空会话占位」的场景。

### 4.4 `PATCH /api/conversations/{conversation_id}`

**为什么用 PATCH 而不是 PUT**：会话还有 `agent_type`、`message_count` 等字段，PUT 语义是「整体替换」，要求客户端提交完整对象。本项目只改标题，PATCH 的「部分更新」语义更准确。

**请求体**

```json
{ "title": "改名后的标题" }
```

**响应 `200`**：返回更新后的完整会话对象。
**错误**：`40401` 会话不存在。

### 4.5 `DELETE /api/conversations/{conversation_id}`

**响应 `204 No Content`**，无响应体。

**级联行为**：该会话下的所有 `message` 记录会被数据库外键 `ON DELETE CASCADE` **自动删除**。前端不需要先删消息。

> **前端注意**：`204` 响应**没有响应体**，不要调用 `res.json()` —— 会抛 `Unexpected end of JSON input`。这是最常见的低级错误之一。

### 4.6 `GET /api/conversations/{conversation_id}/messages`

**查询参数**：`page`（默认 1）、`size`（默认 100，最大 200）

**排序**：按 `created_at` **正序**（对话顺序）。数据库联合索引 `idx_conv_created (conversation_id, created_at)` 同时覆盖过滤与排序。

**响应 `200`**

```json

  "total": 2,
  "page": 1,
  "size": 100,
  "items": [
    {
      "id": 1,
      "role": "user",
```

## 5. L3 系统域

### 5.1 `GET /api/health`

**用途**：演示前跑一次，比现场发现 Neo4j 没启动强。也用于排查「问答报错到底是哪个依赖挂了」。

**响应 `200`**

```json
{
  "mysql": "ok",
  "neo4j": "ok",
  "ollama": "ok",

}
```

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `mysql` | `"ok"` \| 错误描述 | 执行一次 `SELECT 1` 验证连接 |
| `neo4j` | `"ok"` \| 错误描述 | 执行一次轻量查询验证连接与认证 |
| `ollama` | `"ok"` \| 错误描述 | 请求 `/api/tags` 验证服务存活 |

### 6.2 后端 Pydantic v2 模型

```python
# backend/api/schemas.py
from datetime import datetime
from enum import Enum
from typing import Annotated, Literal
from pydantic import BaseModel, ConfigDict, Field

# ── 枚举 ──
class AgentType(str, Enum):
    RAG = "rag"
    GRAPH = "graph"

class MessageRole(str, Enum):
    USER = "user"
    ASSISTANT = "assistant"

# ── 请求体 ──
class AskRequest(BaseModel):
    """问答请求。前端两个 Tab 共用此结构。"""
    model_config = ConfigDict(json_schema_extra={
        "example": {
            "question": "百日咳有哪些症状",
            "conversation_id": None,
            "use_memory": True,
        }
    })

    question: Annotated[str, Field(min_length=1, max_length=2000, description="用户问题")]
    conversation_id: Annotated[str | None, Field(default=None, description="会话 ID，传 null 表示新建")]
    use_memory: Annotated[bool, Field(default=True, description="是否携带历史上下文")]

class ConversationCreate(BaseModel):
    title: Annotated[str, Field(default="新会话", max_length=120)]
    agent_type: Annotated[AgentType, Field(default=AgentType.RAG)]

class ConversationUpdate(BaseModel):
    title: Annotated[str, Field(min_length=1, max_length=120)]

# ── 响应模型 ──
class Source(BaseModel):
    """回答的溯源来源。对应系统设计 §1.6。"""
    type: Literal["vector", "graph"]
    name: str
    score: float | None = Field(default=None, description="图谱类固定为 null")
    snippet: str
    meta: dict | None = None

class Usage(BaseModel):
    """token 用量。仅云端模型产生。"""
    prompt: int
    completion: int
    total: int
    model: str
    latency_ms: int

class Conversation(BaseModel):
    """会话。由 ORM 对象转换而来。"""
    model_config = ConfigDict(from_attributes=True)

    id: str
    title: str
    agent_type: AgentType
    message_count: int
    total_tokens: int
    created_at: datetime
    updated_at: datetime

class Message(BaseModel):
    """消息。user 角色的 sources 与 token 字段均为 null。"""
    model_config = ConfigDict(from_attributes=True)

    id: int
    role: MessageRole
    content: str
    sources: list[Source] | None = None
    prompt_tokens: int | None = None
    completion_tokens: int | None = None
    total_tokens: int | None = None
    model: str | None = None
    latency_ms: int | None = None
    created_at: datetime

class Page[T](BaseModel):
    """通用分页信封。Pydantic v2 原生支持泛型模型。"""
    total: int
    page: int
    size: int
    items: list[T]

class ErrorBody(BaseModel):
    """统一错误信封。"""
    code: int
    msg: str
    detail: str | None = None

class HealthStatus(BaseModel):
    """健康检查。始终返回 200，靠字段值判断。"""
    mysql: str
    neo4j: str
    ollama: str
    faiss_index: str
    bm25_corpus: str
    rerank: str
```

> **Pydantic v2 要点**：
> - 用 `model_config = ConfigDict(...)` 取代 v1 的 `class Config` 内部类
> - `from_attributes=True` 取代 v1 的 `orm_mode = True`（用于从 SQLAlchemy ORM 对象直接构造）
> - 用 `Annotated[T, Field(...)]` 组织约束，这是官方推荐的现代写法
> - 泛型模型 `Page[T]` 是 v2 原生支持，v1 需要 `GenericModel`

**手写补充的流式事件类型**（OpenAPI 无法描述 NDJSON 流，这部分需手写）：

```ts
// src/types/stream.ts
import type { components } from './api';

type Source = components['schemas']['Source'];
type Usage = components['schemas']['Usage'];

export type StreamEvent =
  | { sid: string }        // 新建会话时首行下发
  | { c: string }          // 正文增量
  | { s: Source[] }        // 溯源来源
  | { u: Usage }           // token 用量
  | { err: string };       // 错误，收到后流终止
```

> **OpenAPI 描述不了流式协议**，这是它的固有局限。所以 §3.4 必须用文字写清楚，且这部分是前后端最需要对齐的地方 —— 也是本文档存在的主要理由。
>
> **实现时的改进**：判别联合类型 `{sid} | {c} | {s} | {u} | {err}` 仍需手写，但其中两个**嵌套结构**不必再手抄 ——
> 后端在 `/api/ask` 的 `responses` 里把 200 响应的 `model` 声明为 `StreamEvent`，借此把 `StreamEvent`、`Source`、`Usage`
> 一并写进 `components.schemas`。前端 `npm run api:types` 生成后可直接引用 `components['schemas']['Source']` / `['Usage']`，
> 字段变更也不会漏改。
>
> 注意该写法会让 FastAPI 额外补一条 `application/json` 的 content 条目（而这两个端点是纯 NDJSON 流），
> 后端已在 `chat_api.py` 里做 OpenAPI 后处理把它去掉，`/docs` 上看到的仍是准确的协议。

### 6.4 字段字典（易混淆项）

| 字段 | 类型 | 易错点 |
| --- | --- | --- |
| `conversation_id` | string(UUID) | 是 **UUID 字符串**，不是数字。数据库用 `CHAR(36)` |
| `id`（message） | integer | 消息 ID 是**自增整数**，与会话 ID 类型不同，别混用 |
| `score` | number \| null | 图谱来源**固定为 null**，前端做数值格式化时要判空 |
| `created_at` / `updated_at` | string | ISO 8601 **带时区**（`+08:00`），不是 naive 时间 |
| `latency_ms` | integer | 单位毫秒，不是秒 |
| `meta` | object \| null | 结构随 `type` 变化，前端用索引签名接收 |

### 7.3 路由实现要点

```python
# backend/api/routers/ask.py
import json
from typing import Annotated
from fastapi import APIRouter, Depends, HTTPException
from fastapi.responses import StreamingResponse

from api.schemas import AskRequest
from api.deps import get_db, get_repo
from agent.rag_agent import stream_agent

router = APIRouter()

@router.post(
    "/ask",
    summary="医疗健康问答（流式）",
    response_class=StreamingResponse,
    responses={
        200: {
            "content": {"application/x-ndjson": {}},
            "description": "NDJSON 事件流，事件类型见接口文档 §3.4",
        }
    },
)
async def ask(
    payload: AskRequest,
    repo: Annotated[ConversationRepository, Depends(get_repo)],
):
    conversation_id = payload.conversation_id or repo.create_conversation()

    async def event_stream():
        # 1) 新建会话时先下发 sid
        if payload.conversation_id is None:
            yield _line({"sid": conversation_id})

        # 2) 正文增量
        answer_parts: list[str] = []
        async for chunk in stream_agent(payload.question, conversation_id, payload.use_memory):
            answer_parts.append(chunk)
            yield _line({"c": chunk})

        # 3) 溯源 → 4) 用量（顺序固定，见 §3.4.3）
        if sources := _collect_sources():
            yield _line({"s": sources})
        if usage := _collect_usage():
            yield _line({"u": usage})

        # 5) 落库（同一事务写 user + assistant 两条消息）
        repo.save_turn(conversation_id, payload.question, "".join(answer_parts), sources, usage)

    return StreamingResponse(
        event_stream(),
        media_type="application/x-ndjson; charset=utf-8",
        headers={
            # 防止反向代理（Nginx 等）缓冲流式响应，导致前端"卡住不动然后一次性全出来"
            "X-Accel-Buffering": "no",
            "Cache-Control": "no-cache",
        },
    )

def _line(obj: dict) -> str:
    """序列化一行 NDJSON。ensure_ascii=False 保证中文可读。"""
    return json.dumps(obj, ensure_ascii=False) + "\n"
```

**四个容易写错的点**：

1. **`ensure_ascii=False`** —— 不加的话中文全部变成 `\uXXXX` 转义
2. **`X-Accel-Buffering: no`** —— 不加的话经代理后流式会变成一次性输出
3. **`media_type` 要带 `charset=utf-8`** —— 否则某些客户端按 latin-1 解码
4. **异常发生在流开始之后时，不能再改 HTTP 状态码** —— 响应头已发送，只能下发 `err` 事件

```python
from typing import Annotated, Generator
from fastapi import Depends
from sqlalchemy.orm import Session

from db.session import SessionLocal
from db.repository import ConversationRepository

def get_db() -> Generator[Session, None, None]:
    """每请求一个数据库会话，请求结束自动关闭。"""
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

def get_repo(db: Annotated[Session, Depends(get_db)]) -> ConversationRepository:
    return ConversationRepository(db)
```

### 7.5 异常处理与错误码映射

```python
# backend/api/errors.py —— BizError 与统一异常处理器
from fastapi import Request
from fastapi.responses import JSONResponse
from api.schemas import ErrorBody

class BizError(Exception):
    """业务异常。code 见接口文档 §1.5。"""
    def __init__(self, code: int, msg: str, detail: str | None = None):
        self.code, self.msg, self.detail = code, msg, detail

@app.exception_handler(BizError)
async def biz_error_handler(request: Request, exc: BizError):
    # 业务码 → HTTP 状态码 的映射表
    http_status = {40001: 400, 40401: 404, 50001: 500,
                   50002: 500, 50003: 502, 50004: 503}.get(exc.code, 500)
    return JSONResponse(
        status_code=http_status,
        content=ErrorBody(code=exc.code, msg=exc.msg, detail=exc.detail).model_dump(),
    )
```

> **实现时的一处调整**：初稿把 `BizError` 放在 `chat_api.py` 里，但那样会**循环导入** ——
> 路由模块需要 `raise BizError(...)`，而 `chat_api.py` 又要 import 路由来注册。因此拆出
> `api/errors.py`，依赖变成单向：`errors.py` ← `routers/*` ← `chat_api.py`。
>
> 同时 `errors.py` 里还多注册了两个处理器：`RequestValidationError` → `40001`
> （不接管的话 FastAPI 会返回自己的 `{"detail": [...]}`，前端按统一信封解析会拿到 undefined）、
> 以及兜底的 `Exception` → `50000`，保证任何未预期异常也是结构化信封而不是裸 500。

**在业务代码中抛出**：

```python
if not conversation:
    raise BizError(40401, "会话不存在", f"conversation_id={cid} 未找到")
```

> **注意**：`50004`（重排不可用）**不应被抛出**。重排失败要静默降级为 RRF 结果，链路继续走完。这个错误码只用于日志，不进响应 —— 详见 §1.5。

### 8.3 客户端封装

```ts
// src/lib/api-client.ts
import createClient from 'openapi-fetch';
import type { paths } from '@/types/api';

export const api = createClient<paths>({
  baseUrl: '/',          // 走 Vite 代理，不写死域名
});

export class ApiError extends Error {
  constructor(public code: number, public msg: string, public detail?: string | null) {
    super(msg);
    this.name = 'ApiError';
  }
}

/** 统一解包错误信封（见 §1.3） */
export async function unwrap<T>(p: Promise<{ data?: T; error?: unknown; response: Response }>): Promise<T> {
  const { data, error, response } = await p;
  if (error) {
    const e = error as { code: number; msg: string; detail?: string | null };
    throw new ApiError(e.code ?? response.status, e.msg ?? '请求失败', e.detail);
  }
  return data as T;
}
```

### 8.4 流式 NDJSON 消费

`openapi-fetch` **不支持流式响应** —— 这是它的设计边界（它面向的是普通 JSON 请求）。流式接口必须用原生 `fetch` 手写，参考实现见 §3.5。

**约定**：把流式消费封装成一个独立 hook，组件不直接碰 `ReadableStream`：

```ts
// src/hooks/useChatStream.ts
export function useChatStream() {
  const [answer, setAnswer] = useState('');
  const [sources, setSources] = useState<Source[]>([]);
  const [usage, setUsage] = useState<Usage | null>(null);
  const [status, setStatus] = useState<'idle' | 'streaming' | 'settled' | 'error'>('idle');
  const abortRef = useRef<AbortController | null>(null);

  const send = useCallback(async (payload: AskRequest) => {
    setAnswer(''); setSources([]); setUsage(null); setStatus('streaming');
    abortRef.current = new AbortController();

    try {
      await streamAsk(payload, (e) => {
        if ('sid' in e) setConversationId(e.sid);
        else if ('c' in e) setAnswer(prev => prev + e.c);
        else if ('s' in e) setSources(e.s);
        else if ('u' in e) { setUsage(e.u); setStatus('settled'); }
        else if ('err' in e) { setStatus('error'); throw new ApiError(0, e.err); }
      }, abortRef.current.signal);
    } catch (err) {
      if ((err as Error).name !== 'AbortError') setStatus('error');
    }
  }, []);

  const stop = useCallback(() => abortRef.current?.abort(), []);

  return { answer, sources, usage, status, send, stop };
}
```

### 8.5 TanStack Query 使用

**只用于普通 JSON 接口**（会话列表、历史消息）。流式接口用上面的 hook。

```ts
// src/hooks/useConversations.ts
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

export const conversationKeys = {
  all: ['conversations'] as const,
  list: (page: number) => [...conversationKeys.all, 'list', page] as const,
  messages: (id: string) => ['conversations', id, 'messages'] as const,
};

export function useConversations(page = 1) {
  return useQuery({
    queryKey: conversationKeys.list(page),
    queryFn: () => unwrap(api.GET('/api/conversations', { params: { query: { page, size: 20 } } })),
  });
}

export function useDeleteConversation() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: string) => unwrap(api.DELETE('/api/conversations/{conversation_id}', {
      params: { path: { conversation_id: id } },
    })),
    onSuccess: () => qc.invalidateQueries({ queryKey: conversationKeys.all }),
  });
}
```

> **TanStack Query v5 语法变更**：v5 移除了数组形式的调用（`useQuery(key, fn)`），**必须**用对象形式 `useQuery({ queryKey, queryFn })`。网上大量 v4 教程仍用旧写法，照抄会报错。

**一轮问答结束后的缓存失效**：流结束后，该会话的消息与列表都需要刷新：

```ts
qc.invalidateQueries({ queryKey: conversationKeys.messages(conversationId) });
qc.invalidateQueries({ queryKey: conversationKeys.all });
```

### 8.6 错误处理约定

| 场景 | 处理 |
| --- | --- |
| HTTP 非 2xx | 解析错误信封，`toast.error(msg)` 展示面向用户的 `msg` |
| 流中收到 `err` 事件 | 在气泡内显示红色提示，**保留已生成的内容**，不要清空气泡 |
| `40401` 会话不存在 | 从本地列表移除该会话并刷新列表 |
| `50004` 重排不可用 | **无需处理** —— 服务端已静默降级，前端收不到 |
| 用户主动中止 | `AbortError` 需单独判断并**静默忽略**，不要弹错误提示 |

## 9. 契约变更流程

接口是前后端唯一的耦合点，变更必须走流程：

1. **谁要改** → 在群里说明「改哪个接口、为什么、影响谁」
2. **确认影响面** → 对照 §2 的功能层级表，找出所有调用方
3. **改后端** → 更新 `schemas.py` 与路由，确保 `/openapi.json` 同步变化
4. **重生成类型** → 前端跑 `npm run api:types`
5. **修编译错误** → TypeScript 会把所有不匹配的地方报出来，逐个修
6. **同步本文档** → 更新 §3 / §4 / §5 对应章节与 §10 修订记录

> **禁止的做法**：后端改了字段名但没重生成前端类型。这会让类型定义与实际响应脱节，比没有类型更危险 —— 因为它会给出**错误的**类型保证。
