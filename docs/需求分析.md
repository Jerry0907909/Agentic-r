## 1. 需求收集

### 1.1 项目背景

`agentic-r` 是 9.16 起新建的 Agentic RAG 工程，已在本地跑通一条最小可用链路：

- **智能体骨架**：LangGraph 的 `agent ⇄ tools` 循环（`agent/rag_agent.py`、`agent/cypher_agent.py`），支持异步流式输出；
- **双工具**：`tools/rag_tool.py`（FAISS 向量检索）+ `tools/cypher_tool.py`（Neo4j 图谱查询，服务端强制只读）；
- **模型层**：本地 Ollama `qwen3:4b` + `nomic-embed-text`，云端 DashScope `qwen3-max`（**此为分析时点的状态**；实现阶段本地模型职责已收窄为只做词嵌入，见 §5.1 决策 D8 与 `系统设计.md` ADR-8）；
- **数据底座**：本地 Neo4j 实例 `Agent_RAG`，医疗知识图谱 **27,395 节点 / 312,387 关系 / 9 类标签 / 10 种关系**（已完成人名噪音清洗）；
- **前端**：单文件 `frontend/index.html`（Vue2 + Element UI CDN），双 Tab、流式渲染已实现。

**但链路目前是断的**，盘点出三处硬缺口：

| 缺口 | 证据 | 影响 |
| --- | --- | --- |
| 医疗向量库不存在 | `agentic-r/faiss-index/` 下只有 `default`（Spring Boot 语料）；而 `.env` 写着 `FAISS_INDEX_NAME=medical` | `retrieve_context` 一调用即抛 `FileNotFoundError`，RAG 链路不可用 |
| 后端接口层为空 | `api/chat_api.py` 为 0 字节空文件 | 前端两个 Tab 请求 `/api/ask`、`/api/ask_graph` 全部打不通 |
| 无任何对话持久化 | 代码中无数据库访问 | 刷新即失忆，多轮对话无法进行 |

因此本次优化的定位是：**补齐断点 + 按需求单做能力增强**，而不是推倒重来。

### 1.2 业务目标

| 层次 | 目标 | 衡量方式 |
| --- | --- | --- |
| 业务目标 | 让普通用户用自然语言问医疗问题，得到**可信、可追溯、交互自然**的回答 | 演示时能完整走通「提问 → 检索 → 溯源 → 追问」 |
| 课程目标 | 完整体验「需求分析 → 系统设计 → 开发实现」的软件工程流程 | 产出物齐全：需求分析、设计文档、可运行系统 |
| 技术目标 | 把「Agentic RAG」从名词变成能说清的技术实现 | 能讲明混合检索、重排、溯源、记忆各自的实现位置与取舍 |

### 1.3 目标用户与典型场景

| 用户角色 | 特征 | 核心诉求 |
| --- | --- | --- |
| 普通用户（主） | 不懂医学术语 | 用大白话提问；答案能看懂；**知道答案从哪来**（不能是黑箱） |
| 医学生 / 从业者 | 有术语基础 | 要结构化结果（症状 / 药物 / 饮食 / 检查 / 科室）；要能追多跳关系 |
| 课程验收方 | 教师 / 助教 | 看架构分层、代码质量、演示流畅度、文档完整度 |

**典型场景**

1. 普通用户问「百日咳的症状有哪些」→ 走图谱，返回结构化症状列表 + 图谱来源标识。
2. 普通用户问「百日咳是什么病、怎么预防」→ 走向量检索，返回描述性文本 + 文档来源与相似度。
3. 用户追问「那能吃什么」→ 系统**记得上一轮在聊百日咳**，无需重复病名。
4. 用户关掉浏览器第二天再来 → 左侧能看到昨天的会话，点开即恢复全部历史。
5. 用户不方便打字 → 点麦克风说话，识别结果直接填进输入框。

#### F1 前端页面美化（React 工程化重构）

- **现状**：`frontend/index.html` 单文件 500 行，Vue2 + Element UI + marked + highlight.js 全靠 CDN 引入；样式内联在 `<style>` 里；双 Tab（「Agentic RAG 对话」/「医疗疾病问答」）用 `sessions` 对象手写隔离。
- **目标**：重构为 **Vite + React 19 + TypeScript + Tailwind CSS + shadcn/ui** 的正式前端工程。
- **关键点**：
  - 保留双 Tab 交互与流式打字机效果（现有体验不能退化）；
  - 双入口保持同级，面向用户显示“医疗健康问答 / 知识图谱查询”；前者面向症状、疾病、用药与健康困扰并只使用医学文档检索，后者只使用知识图谱；点击顶部入口进入对应模式的新页面，只有点击侧栏历史项才加载历史并切换对应入口；会话计数面向用户显示问答轮次而非底层消息条数（见 `前端设计规范.md`）；
  - Markdown 渲染 + 代码高亮（`react-markdown` + `remark-gfm`）；
  - 新增四类 UI 元素：**溯源卡片**（F4）、**token 用量**（F5）、**会话列表**（F7）三处展示位，以及**麦克风按钮**（F8）一处交互控件；
  - 响应式布局 + 亮/暗主题切换。
- **验收标准**：`npm run dev` 一条命令起服务；双 Tab 流式回答正常；四类新增 UI 元素均可见且数据正确。

#### F2 内存级多轮记忆

- **现状**：`stream_agent()` 每次只传 `{"messages": [HumanMessage(content=question)]}`，**不携带任何历史**，每个问题都是独立的。
- **目标**：引入 LangGraph 的 `MemorySaver` checkpointer，用 `thread_id` 区分会话，实现进程内多轮上下文。
- **关键点**：
  - `_build_graph()` 编译时挂 `checkpointer=MemorySaver()`；
  - `graph.astream(input, config={"configurable": {"thread_id": conversation_id}})`，即**会话 ID 直接作为 `thread_id`**；
  - **会话 ID 由服务端生成**：新建会话时前端传 `conversation_id: null`，服务端创建后通过流的**首行 `sid` 事件**回传，前端记录后用于后续请求；续聊已有会话时前端直接回传该 ID；
  - **冷启动回灌**：进程重启后首次访问某会话时，checkpointer 中无上下文，需从 MySQL 读取历史并一次性 `update_state` 回灌（详见 `系统设计.md` §1.7）。
- **边界**：内存级 = **进程重启即失**。长期留存由 F7 负责，两者是互补而非重复（见 §3.3 假设 3）。
- **验收标准**：连续问「百日咳有哪些症状」→「那能吃什么」，第二问不出现病名也能正确命中百日咳；**重启服务后点开历史会话继续提问，仍能接上前文**。

#### F3 rag_tool 混合检索 + 在线大模型重排

- **现状**：`tools/rag_tool.py` 只做 **FAISS 纯稠密检索**，`similarity_search(query, k=3)`，把 3 段文本拼成一个字符串返回。中文短查询、专有名词（药名、检查项）召回差。
- **目标**：**稀疏 + 稠密混合检索 → 融合 → 在线大模型重排**三段式。
- **关键点**：
  - **稀疏通道**：`jieba` 分词 + `rank_bm25`，补齐关键词精确匹配能力；
  - **稠密通道**：现有 FAISS（`nomic-embed-text`），保留语义召回能力；
  - **融合**：RRF（Reciprocal Rank Fusion）合并两路排名，避免两路分数量纲不可比的问题；
  - **重排**：调用 DashScope `gte-rerank` 对融合后的候选做精排，取最终 top-n；
  - **索引侧配套改造**：`utils/rag_index.py` 目前只产出 FAISS 索引，BM25 需要语料分块，必须**同时落盘一份 chunks + metadata**（pickle），否则 BM25 无从建库。
- **前置依赖**：`agentic-r/faiss-index/medical` **当前不存在**，需先执行 `python utils/rag_index.py medical`（约 3 万文本块，实测约 20 分钟）。
- **验收标准**：同一问题下，混合检索的命中率不低于纯向量；重排前后 top-1 结果有可见差异；检索耗时 < 1s（不含重排网络往返）。

#### F4 回答结果溯源

- **现状**：`retrieve_context` 返回拼接字符串，`cypher_tool` 返回 `dict`，**来源信息在返回时就被丢掉了**，前端无从展示。
- **目标**：回答下方以标识列表形式列出内容来源。
- **关键点**：
  - **工具层**：返回值从「裸字符串」改为结构化对象，携带 `sources`，每条含 `type`（`vector` / `graph`）、`name`、`score`、`snippet`；
  - **智能体层**：`AgentState` 增加 `sources` 字段（`Annotated[list, operator.add]`），在工具节点执行后收集；
  - **接口层**：流式协议新增 `{"s": [...]}` 事件（见 §3.3 假设 4）；
  - **前端层**：渲染成溯源卡片，正文中可做角标对应。
- **备注**：这是 8 项里**改动最深**的一项 —— 它要求贯穿「工具 → 状态 → 流式协议 → 前端」四层，任何一层不改都做不成。
- **验收标准**：图谱类回答能标出「来自 Neo4j 图谱：疾病=百日咳，关系=DISEASE_SYMPTOM」；向量类回答能标出「来自文档：{疾病名}，相似度 0.83」。

#### F5 在线大模型 token 统计

- **现状**：`llm/qwen_llm.py` 用 `ChatOpenAI` 直连 DashScope，**没有任何用量采集**。
- **目标**：每次云端调用统计 prompt / completion / total tokens，展示并入库。
- **关键点**：
  - 优先用 `stream_usage=True` 拿到 `usage_metadata`（流式场景可用）；
  - 兜底用 `get_openai_callback()`；本地 Ollama 只负责词嵌入、不产生生成用量，`tiktoken` 估算仅作参考；
  - 前端在每条回答底部展示用量，**会话级累计**由 `conversation.total_tokens` 字段提供（见 F7）；
  - 数据落 `message` 表（F7），便于事后核算成本。
- **注意**：本项目问答**全部走云端模型**，因此 `usage` 事件正常情况下每条回答都会产生。但流式协议仍把它标记为可选，前端按可选项处理 —— 这样将来若接入本地模型，前端不必改动。
- **验收标准**：每条走云端模型的回答下方显示 token 数；数据库 `message` 表能查到对应记录。

#### F6 cypher 只读约束（已完成）

- **现状**：`tools/cypher_tool.py` 已用 `session.execute_read(...)` 执行查询，这是 **Neo4j 服务端强制只读** —— 任何 `CREATE / MERGE / DELETE / SET / REMOVE / DROP` 都会被服务端直接拒绝，比关键词黑名单可靠（黑名单可被字符串、注释绕过，也易误伤正常查询）。
- **配套细节**：写语句不追加 `LIMIT 10`，避免语法错误掩盖真正的「只读模式」提示。
- **可选加固**（列入「可以有」）：写语句前置检测 + 查询审计日志。
- **验收标准**：`CREATE` / `DELETE` / `SET` 均被拒；图谱节点关系数保持不变。

#### F7 历史对话存入数据库

- **现状**：无任何持久化，刷新即失忆。
- **目标**：会话与消息落 **MySQL**，支持历史浏览与恢复。
- **关键点**：
  - 目标库：`agentic_rag`（本机 MySQL 9.6.0，`utf8mb4`）；
  - ORM：SQLAlchemy 2.x + PyMySQL（环境已装，无需额外引入）；
  - 表结构（初版）：

    | 表 | 关键字段 |
    | --- | --- |
    | `conversation` | `id`(PK, UUID) / `title` / `agent_type` / `message_count` / `total_tokens` / `created_at` / `updated_at` |
    | `message` | `id`(PK, 自增) / `conversation_id`(FK) / `role` / `content` / `sources`(JSON) / `prompt_tokens` / `completion_tokens` / `total_tokens` / `model` / `latency_ms` / `created_at` |

    > `message_count` 与 `total_tokens` 是**冗余字段**（可由 `message` 表聚合得出），冗余的目的是让会话列表页免于每页跑 20 次聚合子查询。完整 DDL 见 `系统设计.md` §3.2。

  - 接口：会话列表 / 新建 / 重命名 / 删除 / 按会话拉取历史消息（5 个，详见 `接口文档.md` §4）；
  - **与 F2 协同**：进程内 `MemorySaver` 管短期上下文，MySQL 管长期归档；会话恢复时从库中回灌到 checkpointer。
- **验收标准**：关掉浏览器重开，左侧会话列表仍在；点开历史会话能完整还原消息、溯源与 token 用量。

#### F8 语音输入（纯前端实现）

- **现状**：无。
- **目标**：浏览器原生 `Web Speech API` 实现语音转文字，识别结果填入输入框。
- **关键点**：
  - `window.SpeechRecognition || window.webkitSpeechRecognition`；
  - `lang = 'zh-CN'`，`interimResults = true`，实时把中间结果写入输入框；
  - 浏览器不支持时按钮置灰并给出提示（不静默失败）；
  - **不引入任何后端依赖**，符合需求单「纯前端实现」的限定。
- **风险**：大陆环境下 Chrome 的语音识别实际依赖 Google 在线服务，可能无响应；Edge 一般可用。**列入风险清单 R1**，验收演示前必须先实测。
- **验收标准**：在受支持浏览器中，点击麦克风说话，文字实时出现在输入框。

#### F9 后端接口层（补齐 `api/chat_api.py`）

- **现状**：空文件。前端已在请求 `http://localhost:8000/api/ask` 与 `/api/ask_graph`。
- **目标**：FastAPI 实现，作为前端与智能体之间唯一的契约层。
- **接口清单**（按功能域分三层，共 8 个；完整定义见 `接口文档.md`）：

  | 层级 | 方法 | 路径 | 说明 |
  | --- | --- | --- | --- |
  | L1 问答域 | POST | `/api/ask` | Agentic RAG 对话（`rag_agent`），流式 |
  | L1 问答域 | POST | `/api/ask_graph` | 医疗疾病问答（`cypher_agent`），流式 |
  | L2 会话域 | GET | `/api/conversations` | 会话列表（分页） |
  | L2 会话域 | POST | `/api/conversations` | 新建会话 |
  | L2 会话域 | PATCH | `/api/conversations/{conversation_id}` | 重命名会话 |
  | L2 会话域 | DELETE | `/api/conversations/{conversation_id}` | 删除会话（级联删消息） |
  | L2 会话域 | GET | `/api/conversations/{conversation_id}/messages` | 拉取历史消息（分页） |
  | L3 系统域 | GET | `/api/health` | 依赖健康检查 |

- **流式协议**（NDJSON 逐行，**向后兼容现有前端**）：

  | 事件 | 含义 | 现状 |
  | --- | --- | --- |
  | `{"sid": "<uuid>"}` | 新建会话时回传真实会话 ID | 新增 |
  | `{"c": "文本增量"}` | 回答内容 | 前端已支持 |
  | `{"s": [ ... ]}` | 溯源来源（F4） | 新增 |
  | `{"u": {...}}` | token 用量（F5） | 新增 |
  | `{"err": "错误信息"}` | 异常，收到后流终止 | 前端已支持 |

- **请求参数**：`question`（必填）、`conversation_id`（新建传 `null`，续聊必传）、`use_memory`（默认 `true`，传 `false` 则单轮问答不带历史）。
- **验收标准**：`/docs` 可看到全部 8 个接口；双 Tab 端到端跑通；异常时前端能显示错误而不是白屏。

### 1.5 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 云端模型首 token < 5s（实测 4.2s）；单次完整回答约 14s；检索 < 1s（实测稠密 50ms + 稀疏 300ms，重排另计网络往返） |
| 可靠性 | 云端 API 超时 / 额度耗尽时降级提示，不得白屏；图谱与向量库任一不可用时，另一条链路仍可工作 |
| 安全 | API Key 仅存 `.env`，不入库、不进前端、不写入任何文档；cypher 服务端强制只读 |
| 可维护性 | 维持分层架构（`llm` / `tools` / `agent` / `api` / `db` / `retrieval` / `frontend`，其中 `db` 与 `retrieval` 为本次新增）；路径与环境变量统一走 `utils/paths.py` 单一真相源 |
| 可观测性 | token 用量、检索耗时、来源信息均可查、可入库 |
| 兼容性 | 支持最新版 Chrome / Edge；窄屏可用（响应式） |
| 合规 | 医疗内容仅作课程演示，界面需标注「不构成医疗建议」免责声明 |

**两处技术细节需提前说明**

1. **DashScope 重排不走 OpenAI 兼容端点**。`gte-rerank` 需调用 DashScope 原生 HTTP 接口，因此**不必安装 `dashscope` SDK**，直接用 `httpx` 发请求即可（项目已用 `trust_env=False` 规避系统代理劫持的既有约定，此处沿用）。
2. **`load_dotenv(override=True)` 必须保留**。`~/.zshrc` 会 source `~/.neo4j/aura.env`，其中导出的 `NEO4J_PASSWORD` 会盖掉项目 `.env` 的值，导致「拿 Aura 的密码连本地库」这类静默认证失败。此坑已修复，改造时不得回退。

- 8 项之间存在**共享改造点**，可合并施工：F4 与 F5 都改流式协议，F2 与 F7 都改会话状态管理，F1 一次性承载 F4/F5/F7/F8 四类展示位。

真正的时间风险集中在 **F1（React 工程从零搭）** 和 **F3（索引重建 20 分钟 + 检索链路重构）**。缓解手段见 §4.2 分阶段计划。

### 2.3 成本可行性

| 成本项 | 说明 |
| --- | --- |
| 本地组件 | Ollama（词嵌入）、Neo4j、MySQL、FAISS 全部本地运行，**零费用** |

### 3.3 边界假设

改造过程中依赖以下假设，**若假设不成立需回到需求阶段重新评估**：

1. **单用户单机运行**：不做并发压力设计，FastAPI 单进程即可。
2. **医疗知识图谱保持只读**：本次不写入图谱，仅查询。
3. **「内存级记忆」与「历史入库」职责分离**：前者管进程内多轮上下文（重启即失），后者管长期归档与恢复。二者不重复实现，通过「恢复会话时从库回灌」衔接。
4. **流式协议向后兼容**：新增事件类型，不改动既有 `c` / `err` 的语义与格式。
5. **重排服务可降级**：DashScope 重排不可用时，退化为「混合检索 + RRF 融合」结果直接返回，链路不中断。
6. **语音输入为增强项**：其不可用不影响系统核心功能，故列为「应该有」而非「必须有」。
